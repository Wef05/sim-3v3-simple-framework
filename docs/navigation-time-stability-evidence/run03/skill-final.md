# Booster 仿真与看板导出

完成用户指定的一次仿真测试，交付可导入现有战术看板的 JSON 和比赛证据。沿用当前项目、策略和指定时长，不自行修改战术或追加比赛。

## 开赛前

- 读取当前项目的 `AGENTS.md`、`agent.toml`、`.booster-studio/project.json` 及实际存在的看板文档，核实虚拟机器人、容器及看板状态。`docs/tactics-dashboard.md` 若缺失，记录缺口并检查当前服务实现及本机运行参考，不假定旧文档存在。历史名称、IP、端口仅作为定位线索。
- 按需阅读[本机运行参考](references/local-runtime.md)，恢复机器人并通过 Studio 构建部署当前项目。开发容器运行不等于仿真就绪。确认 Studio 当前项目指向本任务目录；CUA 读取超时仅表示界面连接失败，按运行参考做有限恢复后再判断是否受阻。用实际 runner 日志核验双方 Agent；可读取 Python 源码时，对比本任务源码、构建包和实际部署文件摘要。包存在、版本号一致不能单独证明已部署当前源码。
- 在激活、重置、部署或清理之前，先检查是否存在正在运行的测试：结合裁判 `/status`、测试调度进程或任务状态及可用的运行标识判断。READY、SET、PLAYING、暂停中的比赛，以及已启动但尚未正式开球的测试均算正在运行；不能只凭容器运行、遥测到达或比分不变判断。状态查询失败或无法排除已有测试时，不清理、不启动新比赛，先排查。
- 已有测试运行时，不清除看板数据、不覆盖部署、不自动接管或终止。保存可取得的状态，说明与新测试的冲突并确认如何处理。
- 无明确保留历史要求时（见“导出与清理”），确认没有正在运行的测试后，在开始新比赛前清除本次测试队伍的看板旧数据：调用 `POST /api/history/clear`，核验响应和历史状态。不清理与本次测试无关的队伍或已导出的本地文件。清理失败时先解决，再开始比赛。
- 确认看板有新鲜快照和本场球员数据，在清理完成后重新读取并记录服务 `session` 和目标队伍 `last_id`，作为开赛边界。接收端可能立即录下新的待机帧，这些不是未清除的旧历史；不得沿用清理前的 session。

- 仿真窗口打开后至少等待 60 秒系统时间，再检查双方 runner 已 Active、看板新鲜及裁判就绪后开赛；等待时长不能替代就绪核验。记录窗口打开/就绪/开赛时间。
- 开赛后检查 READY 入场过程及 PLAYING 开始时双方三名机器人的位置。若机器人持续停留在场外出生点（结合初始坐标、连续位置不变和比赛阶段判断，不能把正常短暂出界或受罚离场当成加载失败），保存本次失败证据后结束本场、通过官方入口重置，再按上述等待与就绪检查重试。这是用户明确指定的无效开局恢复规则；不对战术效果不佳自动追加比赛。只结束自己启动或用户明确授权接管的比赛，每次使用独立目录。

## 计时与结束

优先使用仿真器支持的时长配置，并在开赛前核验裁判时长。如果当前接口只有固定赛制，而用户要求短时测试，可以告知按裁判计时运行指定秒数后主动结束。不能将其称为缩短赛制下的自然完赛；用户明确要求自然完赛时，不使用此替代。

以裁判 `timeRemaining` 的下降量判断经过时间，不能按系统时间等待一分钟就认定比赛一分钟。保存初始值及连续样本，检查重置、时间回退、断联和意外结束。首次开球 READY 通常不扣主时间；进球后 READY 可能扣时，以实际裁判字段为准。

设定适合当前仿真速度的有限等待上限。通常每 0.5–1 秒查询状态，临近终点缩短间隔控制误差。只有本次成功启动的比赛才自动收尾；结束前核对比赛身份和计时连续性，避免结束另一场。失败时保留样本和可取得的回放；除上文用户指定的场外出生点无效开局恢复规则外，不自动重跑。

## 导出与清理

若本任务的用户指令或 `AGENTS.md` 明确要求保留看板历史，则不执行赛前/赛后清空，以 `session`、起止帧 ID 隔离本场并报告采用了保留历史模式。下述清理流程用于没有此类明确保留要求的任务。

停止比赛后等待终态快照到达，或明确记录终态缺失，立即保存该队伍的结束 `last_id`。导出时用 `--until-id` 固定结束边界，分页读取开赛边界之后的帧，确认服务 `session` 未改变。保留历史模式下，其他场次重置可能不改变 session，仍须检查 `context.now` 无回退，不能只验证帧接收时间递增。使用随附脚本：

```sh
python3 scripts/export_dashboard.py --base-url http://127.0.0.1:8765 \
  --team 1 --after-id START_LAST_ID --until-id END_LAST_ID --session START_SESSION \
  --output /absolute/project/results/UNIQUE_RUN/dashboard-team1.json
```

脚本路径相对于技能目录，示例边界须替换为本场实际值。脚本仅导出，不启动比赛或清除历史。服务保留窗口可能截断历史，检查边界和采集跨度；脚本的格式校验不能证明全程无丢帧。

每次使用独立输出目录，保留开赛前状态、开始响应、连续样本、结束状态、可用的 `/result` 和事件记录、runner 日志，以及源码版本和构建包摘要。失败尝试单独留存。按 `soccer-tactics-replay` v1 保留原始帧，不补造缺失位置和时间。

导出文件成功写入后，重新读取文件，核验格式、队伍、帧数和本场时间范围；同时确认必要比赛证据已落盘。只有导出成功且校验通过后，才执行赛后清理；导出失败或校验失败时保留看板原始记录用于重试。

赛后清理前再次确认没有新的测试接管同一看板队伍。通过官方控制入口停止本次测试的 Agent/遥测发送，等待在途数据排空，再调用 `POST /api/history/clear` 清除本次队伍的服务端历史和最新快照。不要为清理而结束其他测试或停止共享看板服务。检查历史为空、最新快照已移除，并在短暂等待后复查无新帧；若仍持续接收，定位本次残留发送源后再清理，避免无限清除。无法停止或无法确认归属时保留数据并说明清理未完成。

最终报告实际比赛秒数、比分、结束方式、帧数、大小和导出文件链接，以及赛后清理是否完成。区分赛前准备、比赛计时和系统录制时长；短时领先不等于完整比赛获胜。
